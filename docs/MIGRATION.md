# Reviewed STATUS-to-LEDGER adoption

`scripts/docs-migrate.py` inventories STATUS before a ledger becomes the source of open work. It uses only Python's standard library and preserves STATUS byte for byte. The operator reviews the mapping and row fields before an explicit write; a preview alone is not a completed adoption.

From the skill repository, inspect a project without changing it:

```sh
python3 -B scripts/docs-migrate.py /path/to/project
```

Doctor and migration use the same register selection contract. Automatic discovery considers the project root and its `docs/` child, and requires `STATUS.md`, `CHANGELOG.md` and `DECISIONS.md` together. A partial or empty competing directory does not win over a complete register. If both candidates are complete, select the owner explicitly with `--register-dir docs` or `--register-dir .`; record ownership in both READMEs. Passing the register directory itself works when it has no competing complete `docs/` child. Both commands print the selected target, and migration binds the reviewed plan to that directory before any write or journal replay.

Pre-install migration remains available only through an explicit path. For a source that has STATUS and CHANGELOG but no DECISIONS, use `--pre-install --register-dir /path/to/source` with the project argument. Supply both flags again on apply. This option does not install the protocol or make a partial register an automatic discovery candidate.

Create a review artifact in an existing directory:

```sh
python3 -B scripts/docs-migrate.py /path/to/project --plan /path/to/project/docs/migration-plan.json
```

The JSON includes the selected register, source records, original text and locations, input fingerprints, existing/new row counts, proposed IDs and a list of unresolved records. List items and table rows are candidates only within named live sections: In flight, Blocked, Deferred, Next, Known issues, Open questions (owner), and Findings. Fenced examples, comments and empty-section markers are excluded. Prose in those sections requires a disposition. Inventory other trackers and custom sections separately before declaring adoption complete.

Table support is deliberately bounded: a leading-pipe header (zero to three leading spaces) must be followed by an equal-width delimiter row. Header and delimiter rows never become findings. Recognised column labels may coexist with custom columns. Every nonempty `Blocked on`, `Blocked-on`, `Blocked by`, `Gate` and `Blocker` cell is retained, in source order, joined by `; `; any remaining gate makes the proposed row BLOCKED. Validation requires every explicit source gate to survive review. Multiple `Status`/`State` cells are accepted only when their nonempty states agree; a conflict or an invalid state leaves the complete source row unresolved. Reconcile that live finding in STATUS and create a new plan before migrating it.

Known state columns accept the whole tokens OPEN, BLOCKED and VERIFYING, case-insensitively, either bare or surrounded by balanced emphasis (`*`, `**`, `***`, `_`, `__`, `___`) or backtick code delimiters. No state is inferred from a phrase such as “requests blocked by CORS” or from a recognised title column. Without a named state column, a standalone state elsewhere in the row makes the layout unresolved, including formatted tokens. A broader refusal guard also catches struck-out tokens, simple links/HTML around a token, HTML entities and incomplete emphasis; those spellings never establish an active state. Bespoke tables without a possible state token remain candidates under D-0018. This is a bounded extraction and ambiguity check, not a Markdown renderer or a natural-language state classifier.

Raw HTML beginning on a block line is opaque to migration. Explicit declaration (`<!...>`), CDATA (`<![CDATA[...]]>`) and processing-instruction (`<?...?>`) blocks are opaque as well. CDATA closes only on the contiguous source delimiter `]]>` and processing instructions only on the contiguous `?>`; a physical newline between delimiter characters does not close either block. Declaration handling retains its bounded subset and quote rules and is not broadened to join delimiter fragments. Incomplete blocks remain one unresolved record for reconciliation. A stack tracks explicit opening and matching closing tags; unclosed or mismatched elements conservatively retain the rest of the source. Python's standard-library HTML tokenizer tracks comments and quoted attributes across lines, so tag-shaped text inside them cannot open or close an element. Adjacent roots on one line stay within the same boundary. A non-raw block ends only at a separating blank line after the complete physical line has been parsed with no open elements or incomplete tag remaining, or at end of file. This also applies to void and self-closing elements: a pipe table immediately after `<br>` or `<div></div>` remains opaque until a blank line separates it from the HTML. Multiline attributes remain within the block. The raw-text elements `pre`, `script`, `style` and `textarea` end at their first closing tag after the opening element, including a close within a comment literal, and do not require a following blank line. Inside a live section, each such block appears as one unresolved source record with its original content, so inner headings, lists and pipe tables cannot become live findings. This intentionally conservative boundary may retain HTML-wrapped content that a renderer would expose as Markdown; it does not infer a DOM or implicit element closures. Reconcile real findings into ordinary supported source lines or explicitly disposition an example; do not silently discard the block. Indented code and unsupported layouts also require reconciliation. Ledger readers exclude HTML examples so their tables cannot become write targets.

Review each new mapping's `row`: priority, status, date, title, tags, closing condition, remaining blockers, touched area and evidence. Fill `closes_when` with an actual yes/no observation and set the mapping's `reviewed` field to `true`. A blocked source must retain a real gate; migration does not authorize execution or silently resolve an owner question. Dates must be valid and no later than the as-of date. Tags must already belong to the ledger's declared vocabulary. For an unresolved record, use `disposition: "context"` or `"duplicate"`, supply a reason, and use `maps_to` for a duplicate. A separate live finding needs to be reconciled into the source and replanned, not dismissed as context.

Keep the generated register path, source keys, counts, IDs and fingerprints unchanged. The command verifies them against current input before applying:

```sh
python3 -B scripts/docs-migrate.py /path/to/project --write --plan /path/to/project/docs/migration-plan.json
```

`--write` requires a saved reviewed plan. Bare `--write` is refused. `--today YYYY-MM-DD` supplies a reproducible as-of date; normal runs use the local date. Existing plan files are read, never overwritten by a preview. To replan after source changes, choose a new JSON filename. Plans created before register-path binding was added must also be regenerated and reviewed; do not add a target to an old plan by hand.

IDs are allocated above all default-series LG numbers found in the register's Markdown files, including archived rows, CHANGELOG, reservation files and pending entry fragments. Numeric aliases reserve the same address; all numeric IDs have a twelve-digit limit including zero padding. Existing prefixed families are accepted and remain distinct from default LG allocation. A live/archive collision requires lifecycle reconciliation before migration proceeds. An unchanged source record retains its source key even when other lines move, and its generated `migration:STATUS.md#...` evidence allows a fresh plan to recognize a prior migration, including after archival. Keep that provenance when editing rows. Editing the source text or moving it to a different section changes its identity; reconcile that change before applying a newly proposed row.

Applying first saves `.docs-migrate-journal.json`, then appends one CHANGELOG entry with counts and mappings, creates an archive when absent, and writes LEDGER. Each file replacement is atomic and flushed. This is a recoverable sequence, not a filesystem-wide atomic transaction: an interrupted run may leave the log ahead of the ledger. Rerun the **same reviewed plan** to finish missing writes without duplicating rows or log entries. The journal verifies expected before/after contents and stops on conflicting intervening edits. Preserve the journal and plan until recovery is complete; completed journals remain as local replay receipts. Use one writer throughout review and apply.

After applying, compare every source finding with the resulting IDs and any explicitly resolved records. Run Doctor, inspect its check levels, then perform ordinary Close: CHANGELOG first, any needed ledger edits, STATUS rewrite last. Replace STATUS lists with counts and current priorities only after coverage is complete. A clean Doctor report verifies structure; it does not verify the meaning of a closing condition or the completeness of a manually reviewed inventory.

Exit `0` means preview or apply completed; it does not mean every candidate is reviewed. Exit `2` reports a refused or failed migration with a diagnostic. A refusal before the journal writes leaves the register unchanged; an I/O failure after it writes is recovered using the same plan.
