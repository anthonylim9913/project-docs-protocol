# Executable verification

From the repository root, run either entry point:

```sh
python3 -B -m unittest discover -v
python3 -B tests/run_regression.py
```

Both discover the same `test_*.py` suite and return a nonzero exit on failure. The explicit runner also refuses an empty suite. Tests use Python's standard library (Python 3.9 or newer). Most scratch projects live under ignored `tests/.tmp/`; Git checks, fresh-install checks and the JSON-mode fixtures use system temporary directories for their independent repositories and ancestor-free registers. Test cleanup removes those temporary projects. They need no private files, credentials or network service. The final local verification environment and actual test count are recorded in [the hardening review](../docs/HARDENING-REVIEW.md).

**What the binding rule and the harness checks establish, and what they do not (D-0025).** `tests/input_manifest.py` binds every file in the repository except its `EXCLUDED` list, and refuses bytecode and import hooks anywhere in the tree (remove a `__pycache__/` left by a run without `-B`). `tests/harness.sha256` lists every file the verdict reads (`HARNESS_FILES`) with its SHA-256, in `sha256sum` format. After editing any of them, regenerate it with `python3 -I -B tests/input_manifest.py . --print-harness-record > tests/harness.sha256`. `run_acceptance.py` and `validate_acceptance.py` re-run themselves under `python3 -I -B` and load the harness only from bytes that match the record.

Run inside the tree it judges, that check is a convenience, not a control. It names accidental or partial edits, planted modules and bytecode, and a wrong pin. It cannot catch an edit to the validator that switches off its own checks, even with the pin supplied, because the pin is then checked by the code that was edited (`InTreeLimitTests` keeps three such mutants). Only the external check below closes that gap. The runner never reports acceptance; only the validator does.

**External check (the reviewer's procedure).** `CANDIDATE` is the candidate checkout. `TRUSTED` is a separate clean checkout of a commit whose harness the reviewer has reviewed: the last reviewed `main`, or, for a change to the harness itself, the candidate's reviewed commit checked out again in a different directory.

```sh
cd TRUSTED
git status --porcelain --ignored            # expect no output except ignored .DS_Store files
sha256sum -c --quiet tests/harness.sha256   # coreutils, not repository code: every harness file matches
PIN=$(sha256sum tests/harness.sha256 | cut -c1-64)   # compare with the pin recorded when the harness was reviewed
HEAD=$(git -C CANDIDATE rev-parse HEAD)
python3 -I -B tests/run_acceptance.py --runtime-root CANDIDATE --source-commit "$HEAD" \
    --result /tmp/acceptance-result.json --harness-sha256 "$PIN"
python3 -I -B tests/input_manifest.py CANDIDATE --out /tmp/candidate-inputs.json
python3 -I -B -c 'import json,sys; json.dump(json.load(open(sys.argv[1]))["files"], open(sys.argv[2], "w"))' \
    /tmp/candidate-inputs.json /tmp/candidate-hashes.json
python3 -I -B tests/validate_acceptance.py --harness-sha256 "$PIN" --subject-root CANDIDATE \
    /tmp/acceptance-result.json tests/fixtures/hardening-2026-09-12/acceptance-cases.json /tmp/candidate-hashes.json
```

The last command prints `{"accepted": true, "cases": 4}` and exits 0, or prints `REJECT: …` and exits 1. Here the trusted manifest generator computes the candidate's input hashes. A reviewer who wants a list that does not come from repository code at all can build it with `git ls-files` and `sha256sum`, leaving out the `EXCLUDED` paths. The trusted code executes the candidate's `scripts/` as the product under test and never imports the candidate's `tests/`. It refuses a candidate whose judging files or record differ from its own, and records the candidate's full input tree digest in the result (`source_provenance.runtime_tree_sha256`). The pin is the SHA-256 of `tests/harness.sha256`, the file that lists every harness file's hash. `python3 -I -B tests/input_manifest.py . --print-harness-digest` prints the same value from repository code.

**Checkout requirements.** The record and the manifest hash bytes, so they assume a checkout with LF line endings and case-preserving paths. An `eol=crlf` or `core.autocrlf=true` checkout, or a case-only rename on a case-insensitive file system, makes the harness check fail closed with `harness files do not match` and a list of files. File modes are not bound: `chmod +x` leaves the manifest unchanged. A nested `.git` directory below the root (for example inside `staging/`) is skipped, with its contents, without a message (see LG-0049).
